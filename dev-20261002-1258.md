# Session write-up: 2026-10-02 — forced re-login investigation

Branch: `cookie-storage-legacy-file-fallback`

## Starting point

Uncommitted working-tree changes already present at session start (rate
limiting on login, transient vs. permanent failure handling for session
resume, JWT-expiry debug logging, cookie rotation persistence). Committed
these first as `3e50b53`.

## Reported symptom

"login, sleep 3m, login -> login again" — the CLI was forcing a full
interactive phone+PIN login far more often than expected, sometimes within
minutes of a successful login.

## Bugs found and fixed

### 1. `c6d0352` — saved session cookie silently lost its `Path` scope on reload

`cookiesHost` was `"https://api.traderepublic.com/api/v1/auth/web"` (includes
a path). `http.CookieJar.Cookies()` only ever returns a cookie's `Name`/
`Value` — never `Path`/`Domain`/`Expires` — so `SaveCookies()` had no real
path info to persist. On reload, `SetCookies()` fell back to RFC 6265's
default-path algorithm using `cookiesHost`, deriving `/api/v1/auth` instead
of the `/` the real server actually sets.

Effect: after every process restart, the restored session cookie was
scoped to `/api/v1/auth/*` and silently omitted from requests to other
paths (e.g. `/api/v2/auth/account`, used by the session-resume check) —
so resuming a saved session looked like it failed, even when the session
was still genuinely valid, forcing an unnecessary full re-login on
essentially every invocation.

Fix: `cookiesHost` changed to a bare origin (no path), so the default path
is `/`, matching the real cookie scope. Added a regression test
(`client_cookies_test.go`) that round-trips cookies through two separate
`Client` instances and checks the cookie is still attached to a different
API path; verified it fails against the old code and passes against the
fix.

### 2. `8f592e8` — JWT-expiry debug logging was dead code

`logJWTExpiry` only decoded cookies literally named `tr_session`/
`tr_refresh`, guessed names that don't match Trade Republic's real cookie
name — so it never actually logged anything, including during a live
repro. Changed to detect JWT-shaped cookie values (3 dot-separated parts,
decodable payload with a non-zero `exp`) regardless of name, so real
`iat`/`exp` evidence could actually be captured.

### 3. `b40f4c7` — confirmed `AUTHENTICATION_ERROR` was misclassified as transient

A live repro (`fetch` with `-v`) produced the following evidence:

```
JWT cookie claims {"cookie": "tr_session", "issuedAt": "...14:45:48", "expires": "...14:50:48", "ttl": 300}
```

Trade Republic's web session JWT has a **hard 5-minute absolute
lifetime**, and hitting `/api/v1/auth/web/session` does not mint a
later-expiring token — it just revalidates the existing one. So an
`AUTHENTICATION_ERROR` ~5-6 minutes after login is expected server
behavior, not a client bug, and there's no way to avoid a periodic full
re-login against this API.

However, handling that expected case crashed the CLI instead of falling
back to login: `sessionRefreshError` only returned `ErrCookiesReset` (the
signal that triggers a graceful re-login) if `ResetCookies()` — best-effort
cleanup of the locally stored cookie — *also* succeeded. In this sandbox
(no D-Bus/keyring available), that cleanup always fails, so a definitive,
server-confirmed `AUTHENTICATION_ERROR` fell through to a generic error,
which the transient-failure handling added in `3e50b53` then treated as
"don't attempt a fresh login" — surfacing a hard crash with a stack trace
instead of the intended clean re-login.

Fix: always return `ErrCookiesReset` when the server reports
`AUTHENTICATION_ERROR`, regardless of whether local cleanup succeeds; log
a cleanup failure as a warning instead of letting it change the
classification. This also fixed a previously-flaky test
(`TestRefreshWebSession_Expired`) that was failing in this exact sandbox
for the same underlying reason.

## Net result

- Session resumption across process restarts now works as long as the
  session is still within its real server-side lifetime (~5 minutes from
  login, not extendable via refresh).
- Once that window passes, the CLI now falls back to a clean interactive
  login instead of crashing.
- `clitr` binary in the repo root is rebuilt after each commit going
  forward (see session memory notes — this was raised as explicit
  feedback mid-session).

## Known constraint (not a bug)

Trade Republic's web session is only valid for ~5 minutes from login and
cannot be meaningfully extended by this client. Any workflow that needs to
stay authenticated longer than that will hit a required re-login; this is
a server-side policy, not something fixable in `clitr`.
